## P1 · Gitee 空仓库不能直接转公开（422）

- **时点**：2026-11-23 18:20
- **现象**：`tools/gitee_release.py --name anatomy3d public` 失败：
  `422 {'error': {'base': ['空仓库不支持设置为公开仓库']}}`
- **对照先例**：mcclone3d 建仓（2026-10-15）走「建仓带 `license_template: MIT` → 自动生成
  Initial commit → 仓库非空 → 转公开成功」。本次工具链的 `create` 子命令实际行为
  （实测 `ls-remote` 返回空、exit 0）表明**远端完全为空**（未生成 Initial commit）。
- **解法**：调整建仓顺序 —— 先本地搭好内容推送，再转公开。首推也因远端为空而
  **无需** `merge --allow-unrelated-histories -X ours`（那是 Initial commit 存在时的处置）。
- **待反哺判断**：这是「工具 create 未带 license_template 参数」还是「Gitee 行为变更」，
  完工后核对 `gitee_release.py` 源码确认，决定是修工具还是改 SPEC-001 铁律 4 的流程描述。

## P4 · CSV 带 BOM 按 utf-8 读 → 首列名 KeyError

- **时点**：2026-11-23 18:40
- **现象**：`load_ta2_index()` 抛 `KeyError: 'ta2_id'`，CSV 首列明明存在。
- **根因**：编辑器写出的 UTF-8 文件带 BOM，按 `encoding="utf-8"` 读入时
  `csv.DictReader` 的第一个字段名变成 `\ufeffta2_id`。这正是 allin 记忆月账
  2026-11-13 21:55 记过的同型坑（「带 BOM 的文件按 utf-8 读会虚增 1 字」）在
  「列名」维度的新形态。
- **解法**：CSV 统一 `encoding="utf-8-sig"`（兼容带/不带 BOM 两种形态），
  写入 `anatomy3d/knowledge/ta2.py` 模块 docstring 作仓内纪律。
- **验证**：selfcheck 与单测修复后全绿（exit 0 / OK 5）。

- **时点**：2026-11-23 18:42

## P6 · README 许可声明形态不符合发布区门禁判据

- **时点**：2026-11-23 19:05
- **现象**：allin `publish_area_gate` 报 `[license.inconsistent] anatomy3d: 缺少声明来源：README`。
- **根因**：README 引用块里的许可行同时含「上游」字样，命中判据的**第三方语境排除词**
  （`第三方|vendor|依赖|兼容|上游|upstream|GPL…`）被排除；强信号正则
  `许可[:：]?[token]` 又被 `**许可**：` 的加粗星号干扰，SPDX 关键词抓不出。
- **解法**：补独立 `## 许可` 章节（判据认 `^#{1,6}\s*许可` 标题后第一段的 SPDX 关键词），
  首提交 `b27b620`。
- **待反哺判断**：规则文档 `rules_docs.py:289` 附近已有两次假阳性修订史；加粗
  `**许可**：` 形态是否值得支持，完工后向 allin 提修订建议（带本例证据）。

## P8 · glTF 导出器把整个文件都导了（17 对象导出 3407 mesh / 162MB）

- **时点**：2026-11-23 20:29
- **现象**：Heart 冒烟导出，stage 场景只有 17 对象（debug 打印确认 `bpy.context.scene.name == 'anatomy3d_stage'`），但 GLB 里 7196 节点 / 3407 mesh、162MB。
- **根因**：Blender 4.2 glTF 导出器不受 `temp_override(scene=…)` 约束地遍历了文件级场景集合——文件里残留的原 Z-Anatomy Scene（约 3400 个带材质的对象）被一并收集。
- **解法**：烘焙完成后**直接移除原场景**（`bpy.data.scenes.remove`），让 stage 成为文件里唯一场景。修后 Heart = 17 节点 / 17 mesh / 2.07MB（缩小 78 倍）。
- **关联坑点①补充**：`new_from_object` 会连材质槽一起拷贝，即使 `mesh.materials.clear()` 后导出器仍尝试走材质节点树报断链 IndexError（与先例描述的 IndexError 同源）；最终以 `export_materials="NONE"` 双保险（注意枚举名是 `NONE` 不是文档直觉的 `NO_EXPORT`，实测报错即知）。

## P9 · Z-Anatomy 的 FONT 对象是 3D 文字标注，不是解剖几何

- **时点**：2026-11-23 20:25
- **现象**：inspect 显示心血管系统 757 对象里 43 个 FONT（各叶子节点亦有）。
- **判定**：FONT 是 Z-Anatomy 场景内的文字标签（对应 audit.json 里 9% 非 TA2 命名的「脚手架几何」的一部分），`new_from_object` 会把它转成文字轮廓网格混进解剖数据。
- **解法**：`GEOMETRY_TYPES` 排除 FONT（仅 MESH/CURVE/SURFACE/META）。

## P10 · TA2.csv 实际格式与直觉不符 + 名称匹配率仅 37%

- **时点**：2026-11-23 20:36
- **现象①**：TA2.csv（Z-Anatomy 仓版）每行整体被双引号包裹 + 分号分隔 + 首行为空行——csv 标准解析把整行当单字段。解法：手动 strip 引号再按 `;` 切分。
- **现象②**：1092 个导出对象仅 402 个（37%）映射到 TA2；先例 Anatria 全图谱口径是 9% 未命名。差距来源：Bonus collection 的对象名带大量变体后缀与拼写偏差（实测 `Right pulonary artery'`——「pulonary」为源数据拼写错误），三段式剥离（`.xx` 后缀 + 尾部 `'`）只覆盖了简单形态。
- **解法（当前）**：仅收录 402 个确定性映射，690 个剔除项全部留档（manifest 构建器 `excluded` 列表）。
- **待办（M3 知识层前）**：加入 TA2 近似匹配（大小写/连字符/复数归一化）、Z-Anatomy 拼写纠错表、两侧人工复核——预期映射率提升到 80%+。**这是 M1 余下系统导出时持续迭代的重点。**

## P11 · 网络环境：GitHub 直连限速 12KB/s，Google 全断

- **时点**：2026-11-23 20:16
- **现象**：Blender 便携包（TUNA 镜像 21MB/s 秒下）；但 Z-Anatomy 资产在 GitHub（直连 12KB/s）与 Google Drive（gdown 挂死，Google 不可达）。
- **解法**：小文件走 jsDelivr CDN（秒级）；大文件走 gh-proxy.com 代理 + 8 线程分块并行（87MB / 4 分钟，支持 Range 206）。mirror.ghproxy.com 已死、ghfast.top 可用但稍慢。
- **沉淀**：大资产获取优先级 = 国内官方镜像 > jsDelivr（<20MB）> gh-proxy 类代理分块并行 > 直连。
